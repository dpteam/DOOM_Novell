# CI и релизы

Два workflow, оба в `.github/workflows/`. Ни один из них не требует IWAD:
ассеты лежат в репозитории, поэтому CI никогда не касается `DOOM2.WAD`.

## `ci.yml` — на каждый push в `main` и на pull request

Четыре задачи, три из которых идут параллельно после быстрой.

### 1. `Data consistency` (~20 с, без SDK)

Дешёвый фильтр, который ловит ошибки в данных раньше, чем запустится движок.

```bash
python -m compileall -q tools        # синтаксис конвейера
python tools/selftest_wadlib.py      # декодеры WAD на синтетическом WAD
python tools/verify_assets.py        # согласованность game/
```

`selftest_wadlib.py` собирает крошечный WAD в памяти (палитра, `COLORMAP`,
патч, флэт, DMX-сэмпл, MUS) и проверяет, что декодеры возвращают ровно то, что
в него положили. Это те самые места, где легко ошибиться: пост-формат патчей,
16 байт паддинга в DMX, «последнее событие несёт дельту» в MUS.

`verify_assets.py` сверяет закоммиченные файлы между собой:

- у каждого шрифта в `fonts.json` есть `.fnt` и атлас, а `lineHeight`/`base`
  совпадают с тем, что записано в самом `.fnt`;
- каждый `font "fonts/..."` в стилях имеет `size`, равный зарегистрированному
  кеглю (иначе Ren'Py 8.5 падает с `FreetypeError`);
- в тексте нет `{size=...}` — для bitmap-шрифта это смертельно;
- всё, что объявлено в `images.rpy`, есть на диске, и наоборот;
- манифест не врёт про количество сцен, карт, звуков и треков.

### 2. `Ren'Py lint` (~1 мин)

Скачивает SDK, запускает `renpy.sh . lint`, проверяет, что в отчёте есть
статистика, и складывает `lint.log` в артефакты.

### 3. `Smoke test` (~2 мин, нужен `lint`)

Гоняет игру целиком на виртуальном X-сервере:

```bash
xvfb-run -a -s "-screen 0 1280x720x24" renpy.sh . test smoke
```

Тест проходит путь: главное меню → архив (три вкладки) → «О проекте» →
настройки → управление → пролог → пять глав с выборами → концовка BFG →
титры → возврат в главное меню. Падает на любом отсутствующем изображении,
незарегистрированном шрифте или недоступной кнопке.

Артефакты: `smoke.log` и `tests/screenshots/*.png` — семь кадров по ходу
прогона (меню, три вкладки архива, карточка главы, первый выбор, итог
забега). Удобно смотреть, что именно сломалось, не запуская игру.

Скриншоты снимаются с `_test.overwrite_screenshots = True`: это улики для
человека, а не golden-image тест, поэтому сравнения с прошлым прогоном нет.

### 4. `Build distributions` (~3 мин, нужен `lint`)

```bash
renpy.sh "$RENPY_SDK/launcher" distribute . \
  --destination dist --no-update \
  --package win --package linux --package mac
```

Три архива (~220 МБ вместе) уходят в артефакт `doom-novell-<sha>` на 14 дней.

## `release.yml` — на тег `v*`

1. Проверяет, что тег совпадает с `config.version` в `game/options.rpy`
   (`v1.1.0` ↔ `1.1.0`). Расхождение — падение, чтобы не выпустить «1.0.0»
   под тегом 1.1.0.
2. **Скачивает FreeDoom и пересобирает ассеты.** Это ключевой шаг: ассеты в
   репозитории извлечены из DOOM2.WAD и принадлежат id Software, поэтому
   распространять их нельзя. FreeDoom — BSD, из него можно.
3. Прогоняет `verify_assets.py` и `lint` на уже пересобранном дереве.
4. Собирает win/linux/mac.
5. **Проверяет манифест внутри архива**: если в `wad_manifest.json` не
   `freedoom`, публикация прерывается. Защита от случайной публикации
   retail-ассетов.
6. Публикует GitHub Release с тремя архивами.

Повторный запуск на существующем теге не падает: ассеты перезаливаются
(`--clobber`), описание обновляется.

Выпуск:

```bash
# версия должна совпадать с config.version
git tag v1.1.0
git push origin v1.1.0
```

Или вручную: Actions → Release → Run workflow → указать тег.

## FreeDoom-сборка в CI

Задача `freedoom` в `ci.yml` делает то же самое на каждый push в `main`:
качает FreeDoom 0.13.0, пересобирает ассеты, гоняет lint и полный smoke-тест,
складывает логи и скриншоты в артефакт `freedoom-build`. Так путь релиза
проверяется постоянно, а не в момент выпуска.

Локально то же самое:

```bash
python tools/build_assets.py --iwad freedoom2.wad --out /tmp/fd
python tools/make_freedoom_build.py --assets /tmp/fd --out /tmp/fd_project
renpy /tmp/fd_project test smoke
```

`make_freedoom_build.py` собирает проект из исходников плюс FreeDoom-ассетов,
перегенерирует `images.rpy` и прогоняет проверки.

## Что видит игрок

Экран «О проекте» показывает, из какого IWAD собран именно этот билд:
`Ресурсы собраны из freedoom2.wad: 3610 lump, SHA-256 …`. Строка берётся из
`wad_manifest.json` через `build_provenance()` в `options.rpy`, поэтому
подделать или забыть её нельзя.

## Кэширование

SDK кэшируется по ключу `renpy-sdk-<os>-<version>`, так что повторные прогоны
не качают 150 МБ заново. Версия задаётся одной переменной `RENPY_VERSION`
в обоих workflow.

## Что CI намеренно не делает

- **Не коммитит пересобранные из FreeDoom ассеты.** Они собираются на лету в
  задаче `freedoom` и в релизе; в репозитории остаётся версия из DOOM2.WAD,
  чтобы локальная сборка выглядела как задумано.
- **Не проверяет звук на слух.** Проверяется только корректность WAV-заголовка
  и число кадров; субъективное качество синтеза — на человеке.
- **Не собирает Android/iOS.** Для них нужен Android SDK и macOS-раннер;
  при необходимости добавляется отдельным job'ом.

## Если что-то упало

| Задача | Что смотреть |
| --- | --- |
| `Data consistency` | лог шага; `verify_assets.py` пишет конкретный файл и строку |
| `Ren'Py lint` | артефакт `lint-report` |
| `Smoke test` | `smoke-test-log` + `smoke-test-screenshots` (7 кадров) |
| `FreeDoom build` | `freedoom-build`: линт, smoke-лог и скриншоты из FreeDoom |
| `Build distributions` | `build-log` и артефакт `doom-novell-<sha>` |
